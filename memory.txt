❯ sentence-transformers 冷启动是什么，要经过什么过程？

● sentence-transformers 冷启动的过程大概是这样：

  python check_embedding.py
    │
    ├─ import sentence_transformers
    │     ├─ import torch          （加载 CUDA 运行时，~几秒）
    │     ├─ import transformers   （Hugging Face 核心库，很重）
    │     └─ import 其他依赖...
    │
    ├─ HuggingFaceEmbeddings(...)
    │     ├─ 实例化 SentenceTransformer
    │     ├─ 从磁盘读模型权重（~1.3GB）到内存
    │     ├─ 把权重转移到 GPU（显存涨起来）
    │     └─ 编译/优化计算图
    │

问：加氢裂化装置的主要反应条件是什么？
答：根据提供的资料，加氢裂化装置的主要反应条件包括：

1. **反应温度**（最关键工艺参数）：
   - 必须严格控制；温度升高可加快加氢裂化反应速度，但过高会降低加氢平衡转化率，过低则裂化反应过慢；
   - 实际操作温度需依据催化剂性能、原料性质（如氮含量高时需提温）和产品要求调整；
   - 运转初期温度可偏低，后期因催化剂积碳失活需逐步提高；
   - 为控制放热温升，各床层需注入冷氢以保护催化剂。

2. **反应压力**（特别是氢分压）：
   - 氢分压是关键，而非总压力；提高压力即提高氢分压（循环氢浓度不变时）；
   - 高压有利于加氢裂化（体积缩小反应）、芳烃加氢饱和、加氢脱氮（比脱硫更依赖高压）；
   - 压力升高虽增加油膜厚度、扩散阻力，但显著提升氢扩散推动力和总体转化率；
   - 原料越重，所需反应压力越高。

综上，**反应温度和氢分压（由反应压力和氢气浓度共同决定）是加氢裂化装置最主要的两个反应条件。**

问：反应器的操作温度和压力范围是多少？
答：根据提供的上下文，反应器的操作温度和压力范围并未直接以明确的数值区间（如“温度范围为X–Y℃，压力范围为A–B

  - 氢分压为 **9.8 MPa** 时，反应温度为 **360°C**；

      173 -### 2.4 Agent 架构思想在 RAG 中的作用
      173 +### 🔲 Level 3 — LangGraph 多步 RAG
      174
      175 -**Agent 的本质**：让 LLM 自己决定"下一步做什么"，而不是固定执行预设流程。
      175 +- 路由节点：判断是否需要检索
      176 +- 评估节点：检索结果充分性判断
      177 +- 改写节点：Query Rewriting，最多重查 2 次
      178 +- Tool Agent：调用 Pandas 分析 xlsx 时序数据
      179
      180 -在朴素 RAG 里，流程是硬编码的：
      181 -```
      182 -问题 → 检索 → 生成   （不管检索结果好不好，都这么走）
      183 -```
      184 -
      185 -引入 Agent 思想（用 LangGraph 实现）后，流程变成：
      186 -```
      187 -问题
      188 - │
      189 - ▼
      190 -[LLM 判断] → 这个问题需要检索吗？
      191 - ├── 不需要（常识性问题）→ 直接回答
      192 - └── 需要 → 检索
      193 -              │
      194 -              ▼
      195 -         [LLM 评估] → 检索结果充分吗？
      196 -          ├── 充分 → 生成答案
      197 -          └── 不充分 → 改写查询，重新检索（最多 N 次）
      198 -```
      199 -
      200 -本项目用 LangGraph 实现这个调度层，核心概念：
      201 -
      202 -```python
      203 -from langgraph.graph import StateGraph
      204 -
      205 -# 状态：贯穿整个 Agent 的共享数据
      206 -class RAGState(TypedDict):
      207 -    question: str
      208 -    rewritten_query: str
      209 -    retrieved_docs: List[Document]
      210 -    answer: str
      211 -    retry_count: int
      212 -
      213 -# 节点：每个节点是一个函数，接收 state，返回更新后的 state
      214 -def retrieve(state: RAGState) -> RAGState: ...
      215 -def evaluate_docs(state: RAGState) -> RAGState: ...
      216 -def rewrite_query(state: RAGState) -> RAGState: ...
      217 -def generate(state: RAGState) -> RAGState: ...
      218 -
      219 -# 边：控制流程走向
      220 -graph = StateGraph(RAGState)
      221 -graph.add_node("retrieve", retrieve)
      222 -graph.add_node("evaluate", evaluate_docs)
      223 -graph.add_conditional_edges(
      224 -    "evaluate",
      225 -    lambda state: "generate" if docs_sufficient(state) else "rewrite",
      226 -)
      227 -```
      228 -
      229 -**Agent 思想对 RAG 的三个具体价值：**
      230 -
      231 -| 能力 | 没有 Agent | 有 Agent（LangGraph） |
      232 -|------|-----------|----------------------|
      233 -| 查询改写 | 固定用原始问题检索 | 检索差时自动改写后重查 |
      234 -| 路由 | 所有问题都走检索 | 简单问题直接回答，省 token |
      235 -| 自我校验 | 不管答案质量直接输出 | LLM 自评，不确定时拒答或重查 |
      236 -
      237 -**一个重要的边界**：LangGraph 的 Agent 不是"无限自由"的，
      238 -它的图结构是我们预先设计的，LLM 只在条件边上做决策。
      239 -这比完全自主的 Agent 更可控、更适合生产环境。

❯ LCEL 链是什么东西？你能简单和我说下嘛？

● LCEL = LangChain Expression Language，本质就是一种用 | 管道符把处理步骤串起来的写法。

  类比 Linux shell：
  cat file.txt | grep "关键词" | wc -l

  LCEL 就是同样的思想，只不过处理的是 AI 链路：
  chain = retriever | format_docs | prompt | llm | StrOutputParser()
  answer = chain.invoke("问题")

  每个 | 左边的输出自动成为右边的输入，从左到右依次执行。

  ---
  为什么要用它，而不是直接写函数调用？

  不用 LCEL 的写法：
  docs = retriever.invoke(question)
  context = format_docs(docs)
  prompt_value = prompt.invoke({"context": context, "question": question})
  response = llm.invoke(prompt_value)
  answer = response.content

  用 LCEL 之后就是上面一行 chain = ...，功能完全一样，但额外获得：
  - .stream() 流式输出（打字机效果）免费送
  - .batch() 批处理免费送
  - 每一步可以单独 .invoke() 调试，出错知道卡在哪

  ---
  本项目里实际用到的样子：

  RunnableParallel(
      answer=chain,        # 同时跑：生成答案
      source_docs=retriever  #         + 拿来源文档
  )

  RunnableParallel 让两件事并行跑，结果合并成一个 dict 返回，这就是为什么 result["answer"] 和 result["source_docs"]
  都有值。

  一句话总结：LCEL 就是把 AI 处理步骤像搭积木一样组合起来的语法糖，核心是 | 管道符。

❯ CUDA残留是什么影响的？如何解决这个问题？

● CUDA 残留是怎么产生的

  正常情况下，Python 进程结束时会自动释放 GPU 显存和 CUDA 上下文。但以下情况会导致残留：

  - Ctrl+C 强制中断（最常见）
  - 程序崩溃/OOM 没有正常退出
  - conda run 启动的后台进程没有结束

  残留进程还占着显存，新进程初始化 CUDA 时发现上下文不干净，就报 unknown error。

  ---
  怎么排查和解决

  # 1. 看谁在占 GPU
  nvidia-smi

  # 2. 找到所有 Python 进程
  ps aux | grep python | grep -v grep

  # 3. 一键 kill 所有占用 GPU 的 Python 进程
  fuser -k /dev/nvidia0 2>/dev/null && echo "已清理"

  # 4. 确认清干净了
  nvidia-smi
