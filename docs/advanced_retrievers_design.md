## 1. 为什么需要高级检索

标准 Hybrid Retriever（BM25 + Dense + RRF）在以下问题上有明显短板：

| 问题类型 | 示例 | 标准检索为何失败 |
|----------|------|----------------|
| **跨段落多跳推理** | "催化剂预硫化完成后，第一次引油应注意什么？" | 答案分散在不相邻的多个 chunk，单 chunk 检索覆盖不全 |
| **宏观综述** | "整个加氢裂化工艺的安全控制体系是什么？" | 需要全文视角，Top-K chunk 只是局部片段 |
| **实体关系推理** | "NiMo 催化剂在高温下性能如何变化？" | 涉及实体间关系，纯向量相似度抓不住关联 |
| **跨章节对比** | "热高分和冷高分的操作参数有什么区别？" | 两个实体在不同章节，需要同时召回两处 |

三种高级检索器分别针对不同短板设计：
- **RAPTOR**：解决"宏观综述"和"跨段落多跳"
- **KG**：解决"实体关系推理"和"跨章节对比"
- **GraphRAG**：两者结合，同时处理局部和全局问题

## 2. RAPTOR — 层级摘要树检索

### 2.1 是什么

RAPTOR（Recursive Abstractive Processing for Tree-Organized Retrieval）是斯坦福 2024 年提出的检索增强方法。核心思想：对文档 chunks 递归聚类，对每个聚类生成 LLM 摘要，构建一棵自底向上的"摘要树"。检索时同时在叶节点（原始 chunk）和根节点（摘要）上搜索。

### 2.2 本项目实现方式

**简化版"Collapsed Tree"方案**（不做递归多层，只做一层摘要）：

```
原始 chunks（400个）
    ↓ KMeans 聚类（k=5~10）
簇0（50个chunk）  簇1（45个chunk）  ...  簇9（40个chunk）
    ↓ LLM 摘要（每簇 150 字）
摘要节点0         摘要节点1         ...  摘要节点9

检索时：
query → base_retriever（搜原始chunk，快）→ top-k原始结果
query → cosine_sim(summary_embs)（搜摘要，少量计算）→ top-3摘要
合并去重 → 最终 top-k
```

**文件**：`retrievers/raptor_retriever.py`
**缓存**：`data/raptor_cache/{collection}_raptor.json`

### 2.3 优点

- **宏观问题召回率大幅提升**：摘要覆盖一整个主题区域，宽泛问题不再只召回片段
- **零侵入现有流程**：只是在返回结果里加入摘要节点，后续 Reranker 正常工作
- **磁盘缓存**：第一次构建后（LLM 调用一次性开销），后续复用，重启不重建
- **实现简单**：scikit-learn KMeans，无额外依赖

### 2.4 缺点

- **首次构建慢**：需要嵌入所有 chunk + LLM 生成摘要（100 chunks × 1 秒/摘要 ≈ 10-15 分钟）
- **摘要质量依赖 LLM**：API 不稳定或 LLM 能力差时摘要价值低
- **单层树**：论文原版是递归多层，本实现只有一层，对极长文档效果打折

### 2.5 为什么这么实现

论文原版用 UMAP 降维 + GMM 聚类，但：
- UMAP 在 WSL 环境安装困难（C 扩展依赖）
- GMM 对小数据集（< 200 chunk）不稳定
- 本项目文档以工业规程为主，单个 collection 通常 400~800 chunk，一层树足够

## 3. 知识图谱检索（KG Retriever）

### 3.1 是什么

传统 RAG 把文档切成 chunk，检索时每个 chunk 独立参与向量匹配，**丢失了 chunk 之间的实体关系**。知识图谱检索在此基础上建一张"实体-chunk"图，检索时通过图遍历找到实体关联的相关 chunk，补充向量检索的盲区。

### 3.2 本项目实现方式

**"实体-chunk 二部图"方案**：

```
构建阶段：
每个 chunk → LLM 提取关键实体（5个以内）
                    ↓
         NetworkX 二部图
         chunk_id_1 ── 加氢裂化
         chunk_id_1 ── NiMo催化剂
         chunk_id_2 ── NiMo催化剂   ← chunk1 和 chunk2 通过实体相连
         chunk_id_3 ── 操作温度

检索阶段：
query → 提取查询实体（如"NiMo催化剂"）
     → graph.neighbors("NiMo催化剂") → [chunk_id_1, chunk_id_2, ...]（共现 chunk）
     → 合并 base_retriever 结果 + 图扩展结果
```

**文件**：`retrievers/kg_retriever.py`
**缓存**：`data/kg_cache/{collection}_kg.json`（边列表）

### 3.3 优点

- **实体关联检索**：两个不相邻的 chunk 如果包含同一实体，会被一起召回
- **跨章节对比**：查"热高分 vs 冷高分"能同时拉到两个章节的 chunk
- **轻量**：NetworkX 纯 Python，无额外数据库依赖
- **可解释**：图结构可视化，能直观看到哪些 chunk 通过哪些实体连接

### 3.4 缺点

- **实体提取质量**：LLM 提取的实体可能不一致（"NiMo催化剂"和"镍钼催化剂"视为不同实体）
- **图规模随 chunk 数线性增长**：10,000 chunk 的图遍历仍然快，但构建时 LLM 调用次数多
- **首次构建慢**：400 chunk / 20 批 = 20 次 LLM 调用（每次包含 20 个 chunk 的文本）
- **实体抽取无消歧**：同名实体不区分（如"压力"可能对应不同上下文）

### 3.5 为什么这么实现

工业规程文档有大量专有名词（催化剂型号、设备名称、工艺参数），这类实体在文档中有强关联性，实体图能有效捕捉。选择 NetworkX 而非 Neo4j，原因是：
- 单机部署，无需额外服务
- 图规模小（< 10 万节点）
- 性能足够（图遍历 < 10ms）

## 4. GraphRAG — Local + Global 双路检索

### 4.1 是什么

GraphRAG 由微软 2024 年提出，核心创新是引入"社区摘要"做**全局搜索**（Global Search），解决 RAG 无法回答需要全文视角的宏观问题。同时保留基于实体的**局部搜索**（Local Search）处理具体事实类问题。

本项目实现参考了 LightRAG（港大，2024）的轻量化思路，不依赖 lightrag-hku 包。

### 4.2 本项目实现方式

```
构建阶段：
1. 实体图构建（同 KG Retriever）
2. 社区检测：对 chunk 嵌入做 KMeans → 同一聚类 = 一个"社区"
3. 社区摘要：每个社区的代表 chunk 用 LLM 生成 150 字摘要

检索阶段：
query
  ├─ Local Search（60%权重）：
  │    提取查询实体 → 图遍历 → 相关 chunk
  │    + base_retriever 基础检索
  │
  └─ Global Search（40%权重）：
       query 与社区摘要做余弦相似度 → Top-2 社区
       → 社区摘要文档 + 该社区前3个 chunk

合并去重 → top-k
```

**文件**：`retrievers/graphrag_retriever.py`
**缓存**：`data/graphrag_cache/{collection}_entities.json` + `_communities.json`

### 4.3 优点

- **同时覆盖局部和全局**：一次检索既能回答具体参数，也能回答体系性问题
- **社区摘要补充上下文**：返回给 LLM 的不只是孤立 chunk，还有该主题的宏观摘要
- **两路权重可调**：`local_weight=0.6` 可按需调整
- **无额外重量依赖**：只用 scikit-learn + networkx，避免安装 lightrag-hku

### 4.4 缺点

- **构建开销最大**：需要实体提取 + 社区摘要，LLM 调用次数 = KG + RAPTOR 之和
- **两个缓存需分别管理**：实体图和社区摘要各一个 JSON 文件
- **社区划分粗糙**：用 KMeans 代替真正的图社区检测（如 Louvain），社区边界不如原版精准
- **实体歧义问题同 KG Retriever**

### 4.5 为什么这么实现

微软原版 GraphRAG 需要独立的数据库（Neo4j/SQLite），构建一次需要数小时，适合离线建库场景。本项目需要：
- 用户上传文档后即可使用（在线构建）
- 无额外服务依赖
- 构建时间在分钟级而非小时级

因此用"KMeans 社区 + 简化实体图"代替原版，在工业规程这类主题集中的文档上效果接近，开销大幅降低。

## 5. 横向对比与选型依据

### 5.1 能力对比

| 能力 | Hybrid（基线）| RAPTOR | KG | GraphRAG |
|------|-------------|--------|-----|---------|
| 精确事实查询 | ✅ 强 | ✅ 强 | ✅ 强 | ✅ 强 |
| 宏观综述 | ❌ 弱 | ✅ 强 | ❌ 弱 | ✅ 强 |
| 实体关系推理 | ⚠️ 一般 | ⚠️ 一般 | ✅ 强 | ✅ 强 |
| 跨章节对比 | ❌ 弱 | ⚠️ 一般 | ✅ 强 | ✅ 强 |
| 多跳推理 | ❌ 弱 | ✅ 强 | ✅ 强 | ✅ 强 |

### 5.2 成本对比

| 指标 | RAPTOR | KG | GraphRAG |
|------|--------|-----|---------|
| 首次构建时间 | 中（LLM × n_clusters） | 中（LLM × n_chunks/batch） | 高（两者之和） |
| LLM 调用次数 | ~10次（10个聚类） | ~20次（400chunk/20批） | ~30次 |
| 查询时额外开销 | 低（摘要 cosine_sim，<5ms） | 中（图遍历 + LLM 实体提取） | 高（图遍历 + LLM + 社区搜索） |
| 磁盘空间 | 小（<1MB） | 小（<2MB） | 中（<3MB） |

### 5.3 适用场景

| 模式 | 最适合 | 不适合 |
|------|--------|--------|
| **RAPTOR** | 宏观综述、需要跨多个章节的问题 | 精确数值查询（摘要会压缩细节）|
| **KG** | 实体关系推理、跨章节对比 | 无明显实体的问题（如"操作规范有哪些"）|
| **GraphRAG** | 需要同时回答宏观和局部的混合问题 | 对延迟敏感的场景（查询时 LLM 调用较多）|
| **Hybrid（默认）** | 精确事实查询、专有名词检索 | 需要全文理解的宏观问题 |

## 6. 本项目的具体实现决策

### 6.1 为什么选这三种而非其他

**排除的方案**：
- **HyDE（Hypothetical Document Embeddings）**：只改写 query，不改变检索结构，收益有限
- **微软原版 GraphRAG**：需要 Neo4j + 独立构建流程，与现有架构不兼容，构建小时级
- **LightRAG（lightrag-hku）**：独立存储格式，无法复用现有 Chroma collection，需全量重建
- **Self-RAG**：需要专门训练的模型，本地 8GB VRAM 装不下

**选择的三种**共同特点：
1. 复用现有 Chroma collection，无需重新入库
2. 只依赖 scikit-learn + networkx（已安装），无额外服务
3. 接口统一（`invoke(query) -> List[Document]`），零侵入 LangGraph

### 6.2 互斥设计的原因

三种模式设计为互斥而非叠加，原因：
1. **避免重复 LLM 调用**：KG 和 GraphRAG 都做实体提取，叠加会重复计费
2. **检索结果去重困难**：三路结果合并后 top-k 语义会混乱
3. **性能保证**：单模式查询时间可控，多模式叠加延迟难以预期

### 6.3 缓存策略的选择

用 chunk 数量作为缓存失效 key（而非 hash 整个 collection），原因：
- 计算所有 chunk 的 hash 需要遍历全量数据，开销大
- chunk 数量变化（新增/删除文档）是实际重建需求的准确信号
- 极端情况（chunk 总数不变但内容变了）下会使用旧缓存，但这种情况在实际使用中极少

### 6.4 面试表达建议

这三种方案在面试中可以这样讲：

> "标准 RAG 只做向量相似度检索，对宏观问题和实体关系推理效果差。我在项目中实现了三种增强检索器：
> - **RAPTOR**：用 KMeans + LLM 构建摘要树，宏观问题的召回率显著提升
> - **知识图谱**：用 NetworkX 构建实体-chunk 二部图，实体关联推理能力增强
> - **GraphRAG**：融合局部实体搜索和全局社区摘要搜索，兼顾精确和宏观两类问题
> 
> 三种模式都以可选开关形式集成，用户可以在前端按需切换，不影响默认功能。所有构建结果磁盘缓存，首次构建后不重复调用 LLM。"
