# 面试深挖各层的回答方式

> 用"设计决策 + 踩坑 + 取舍"结构回答，不读代码，不说虚话。
> 更新日期：2026-04-07

---

## 答题通用结构（每层都这样说）

```
1. 这一层解决什么问题
2. 我选了什么方案，为什么不选别的
3. 遇到了什么坑，怎么解决的
4. 目前有什么局限，下一步打算怎么改
```

第4点主动说出局限性，比被追问出来更好，说明你对系统有清醒认识。

---

## 文档加载层

**面试官问**：你的文档是怎么处理进来的？

输入有三种格式：PDF、Word、Excel，每种处理方式完全不同。

PDF 用 MinerU 做版面分析，它不是简单 OCR，而是把文档解析成结构化的 block 序列——每个 block 有类型（文字/表格/公式/图片）和页码，这个结构化结果是后面切分质量的基础。

Word 有个坑：`.doc` 是旧版 OLE 格式，Python 的 docx 库根本读不了，解决方案是从 WSL 调用 Windows 的 Word COM 对象把它转成 PDF，再走 MinerU pipeline，绕了一圈但保住了格式精度。

Excel 不走 MinerU，因为它本来就是结构化数据，用 pandas 按行读，每行转成"列名：值"的自然语言格式，直接就是可以检索的文本。

表格是个特殊问题——MinerU 遇到复杂表格时 OCR 会失败，text 字段为空。我们加了一个 VLM 补全步骤，把失败的表格图片发给多模态模型，让它输出 Markdown 格式写回去，结果永久缓存，不重复计费。

## 文本切分层

**面试官问**：你的切分策略是什么？

两阶段切分，从文档特点出发。

第一阶段按 Markdown 标题层级切。MinerU 解析出来的文档天然有标题结构，按 H1/H2/H3 切完之后，每个 chunk 都带着自己属于哪个章节的信息，对检索和溯源很重要。

第二阶段对超长段落按字符数切。分隔符优先级是段落 > 句子 > 逗号，尽量不在句子中间断，保证语义完整性。

表格和公式完全不参与切分，整块保留。原因是切了就没意义——表格切一半，下半段是一堆没有表头的数字，向量化后语义完全丢失。

**局限**：chunk size 512 对工艺文档偏小，关键章节计划调到 1024~1536；列表项前导句处理还没做——"以下情况不适用：（1）核辐射"这种结构，如果 chunk 只有"（1）核辐射"，前导语义就丢了。

## Embedding 与向量库层

**面试官问**：Embedding 模型怎么选的？多个知识库怎么管理的？

模型选 BGE 系列，两个原因：一是中文 MTEB 榜单表现好，二是有多语言版本 bge-m3，做跨语言检索时中英文库用同一个模型，向量空间才对齐，余弦相似度才有可比性。

多知识库有个工程问题：不同知识库可能用不同 Embedding 模型，搞混了就会用 A 模型的向量去查 B 模型建的库，结果完全没意义。我们做了一个 Embedding 注册表，JSON 文件记录每个知识库对应哪个模型，入库时自动写入，查询时自动读取。

向量库用 Chroma 本地持久化，每个知识库是独立 collection，共用同一个存储目录。

## 检索层

**面试官问**：检索链路怎么设计的？为什么混合检索？

三层：混合检索 → Reranker 精排 → 送 LLM。

混合检索是 BM25 加向量，用 RRF 融合。两种方式失败模式不同：纯向量对语义好，但专有名词、型号、具体数值容易漏；纯 BM25 关键词精确，但换个说法就找不到。组合互补，召回率显著提升。

BM25 有个中文特有的坑：默认按空格分词，中文没有空格，整段话被当成一个词，BM25 完全失效。我们发现之前跑的测试其实退化成了纯向量检索，加了 jieba 分词之后才真正发挥混合效果。

Reranker 用 BGE 的 Cross-Encoder。和 Embedding 的 Bi-Encoder 不同——Embedding 把 query 和文档分别编码再算相似度，速度快但粗糙；Reranker 把 query 和文档拼在一起过模型，打精确相关性分，慢但准。所以两段式：粗检 Top-20，精排保留 Top-3。

Reranker 全局单例，2.27GB，只加载一次，所有知识库共享。

## LangGraph 控制流层

**面试官问**：为什么用 LangGraph？流程怎么设计的？

用 LangGraph 而不是普通链，原因是 RAG 不是线性流程，需要条件分支和状态管理。检索质量不达标要改写 query 重试（循环），闲聊不需要检索（分支），工具调用是另一条路径。LCEL 处理有状态的多路分支很难维护，LangGraph 用状态机表达得清楚。

整个图 8 个节点。入口是路由节点，判断走检索、直接回答还是工具执行。

检索后有评估节点，看精排最高分有没有达到阈值：达标生成答案，没达标改写 query 重试，最多两次，改写耗尽进 fallback——先试 Tavily 网络搜索，失败才用 LLM 自身知识兜底，并在答案里标注来源类型，让用户知道不是来自知识库。

路由有两种模式：普通模式让 LLM 输出 retrieve/direct 两个词分类；Function Calling 模式用 bind_tools 让 LLM 直接选工具。默认普通模式，开关控制。

聚合类问题用正则检测——"共有多少家机构"这类直接告知 RAG 只看 top-k 无法计数，不处理的话 LLM 会瞎猜数字。

## 后端服务层

**面试官问**：流式返回怎么实现的？

核心难点：LangGraph 是同步的，FastAPI SSE 是异步的，不能直接对接。

解决方案是 `asyncio.Queue` 做桥接。LangGraph 在线程池里跑，每生成一个 token 往 queue 里放；SSE 协程不断从 queue 取 token 往客户端发。两边通过 `run_coroutine_threadsafe` 打通线程边界。前端收到的是逐字流式输出，首 token 延迟约 1~2 秒。

冷启动问题：第一次请求某个知识库要加载 Embedding、建 BM25 索引，可能 20~30 秒。我们做了启动预热，服务起来后后台自动把所有知识库的 graph 建好缓存，用户第一次请求就是热的。预热非阻塞，不影响服务就绪。

Graph 缓存 key 包含知识库名和检索参数，参数变了重建 graph，同参数复用。

## 跨语言检索层

**面试官问**：跨语言检索怎么做的？

实验发现：单纯换成多语言 Embedding 模型不能解决跨语言检索，根本原因是语言偏置——中文 query 在混合库里向量相似度天然偏向中文文档。

解决方案是分库 + query 翻译。中英文文档分别建库（energy_zh / energy_en），命名上有配对约定。检索时把 query 翻译成另一种语言，同时搜两个库，再做一次 RRF 合并，彻底消除语言偏置。

工程上有个冲突点：如果已开多库并行检索，再套跨语言会导致配对库被重复搜索。处理方式是：检测到当前是多库检索器，就只做 query 翻译（双语 query 各搜一次），不再找配对库。

## 评估层

**面试官问**：你怎么评估 RAG 系统的质量？

用 RAGAS 框架，四个指标：
- **ContextPrecision**：召回的 chunk 里有多少是真正有用的（精度）
- **ContextRecall**：正确答案需要的 chunk 有没有被召回（覆盖）
- **Faithfulness**：生成答案有没有幻觉，是否忠于召回内容
- **AnswerRelevancy**：答案和问题的相关性

测试集用 RAGAS 的 TestsetGenerator 从文档自动生成，当前 10 条，计划扩到 40~50 条，分类评估（事实/推理/否定/表格），因为端到端平均分会掩盖结构性短板。

实测结果：单跳精确类问题 ContextPrecision=1.0，多跳抽象类只有 0.25，说明多跳推理是当前主要短板。
